OpenBSD port of opencode --- maintainer notes
=============================================

Upstream:  https://github.com/anomalyco/opencode
Build:     Bun monorepo; this port patches it to run under Node.js.
Distfile:  "make tarball" creates opencode-v${V}-node-modules.tar.gz.
           Place it in DISTDIR before building, or host it and set
           SITES.node_modules + DISTFILES.node_modules.

Update checklist (each new version)
-----------------------------------

1. Bump V in Makefile, update distinfo for the GitHub tarball.

2. Audit the patch set:

   * Re-generate each patch with "make update-patches".  If a hunk
     fails, the upstream source changed in that area --- inspect
     carefully.  Many patches disable Bun-specific code; if upstream
     made that code more Bun-entangled, the port may need new
     workarounds.

   * Grep the fresh unpacked source for new Bun globals, bun: imports,
     or Bun-only TypeScript syntax.  Common patterns to look for:

       Bun.stringWidth   -> needs string-width patch
       Bun.stdin / Bun.file / Bun.write  -> needs Node fs replacement
       import … from "bun" / "bun:ffi" / "bun:sqlite"
       typeof Bun !== "undefined"
       catalog: in any package.json   -> must resolve to a concrete version

   * If upstream added new workspace packages, check that each
     contains no "catalog:" or "workspace:*" references after applying
     the port's import-rewriting patches.

3. Regenerate the node_modules tarball:

       make tarball

   This fetches the NEW upstream source, applies ALL patches, runs
   "npm install --workspaces", adds tsx, and packs node_modules/.

   Watch for npm errors:
   - "Unsupported URL Type catalog:"  -> a catalog: reference survived
     the patches.  Add it to the catalog-rewriting patch or resolve it
     manually.
   - Platform-conditional native modules (node-pty, parcel watchers).
     They ship prebuilt binaries for platforms we do not target.  The
     "npm install --force" step tolerates them; rebuild what we need
     in do-build with "npm rebuild".

4. Check that the wrapper in files/opencode still points to a valid
   entry point.  If upstream moved the CLI entry, update the path.

5. Run the full port cycle on an OpenBSD machine:

       make clean fetch makesum patch configure build fake
       make update-plist
       make port-lib-depends-check
       make package

   Then install and smoke-test: "opencode" should start and accept a
   prompt.  If it crashes with a module-not-found error, a dependency
   is missing from node_modules --- re-run "make tarball".

Patch categories (for reference)
---------------------------------

A. Bun runtime removal (~ 15 patches)
   Bun.stringWidth  -> string-width npm package
   Bun.stdin.text() -> Node stream reader
   Bun.file / Bun.write -> fs/promises
   Bun.hash         -> Hash.fast (core utility)
   bun:sqlite       -> stubbed (Zed editor disabled)
   bun:ffi          -> stubbed (win32 terminal disabled)
   import … "bun"   -> "url" (pathToFileURL, fileURLToPath)
   typeof Bun …     -> removed or replaced

B. Plugin disablement (~ 8 patches)
   Upstream plugin loading depends on Bun for npm install + dynamic
   import.  All plugin origins are rejected and the "plug" CLI
   command fails immediately.  If upstream makes plugin support
   runtime-independent, revisit these patches.

C. Self-upgrade / uninstall / package-manager probing (~ 5 patches)
   Updates must come from OpenBSD packages.  The "upgrade" and
   "uninstall" commands are disabled.  The installation-detection
   code is stripped of Bun/npm/pnpm/brew/scoop/choco references.

D. Dependencies & build (~ 3 patches)
   "catalog:" references in package.json files are resolved to
   concrete versions from the upstream Bun workspace catalog.
   "workspace:*" is rewritten to "*" for npm compatibility.
   The "string-width" package is declared explicitly for Node builds.

E. Ripgrep removal (1 patch)
   packages/core/src/ripgrep.ts is replaced with a pure Node.js
   implementation using the "glob" npm package for file discovery
   and built-in RegExp for content search.  No binary dependency.

F. Bun permission arity / test data (2 patches)
   "bun", "bun run", "bun x" entries removed from the permission
   arity table and installation test data.

Architecture constraints
------------------------

* NO external binaries beyond the Node.js runtime.  ripgrep is
  replaced; Bun is replaced.  The only RUN_DEPENDS is lang/node.

* NO network access during "make build".  All npm packages arrive
  inside the node_modules tarball.

* NO native modules beyond what "npm rebuild" can handle (node-pty).
  If upstream adds new native addons, audit their portability.

* Plugin support is intentionally disabled to avoid Bun-dependent
  npm install + dynamic import paths.  Revisit when Bun is available
  on OpenBSD or upstream decouples plugins from Bun.

* Zed editor integration requires bun:sqlite; disabled with a stub
  class that silently returns empty results (no crash).  The stub
  Database class must remain a no-op, not throw.

Known functional differences vs. upstream
-----------------------------------------

These are inherent to the Node.js replacement and are NOT bugs:

* String width: the "string-width" npm package may compute slightly
  different widths than Bun.stringWidth for certain Unicode
  characters (combining marks, emoji sequences).  This affects
  cursor positioning in the TUI prompt.

* RegExp vs. ripgrep regex: the grep tool uses JavaScript RegExp
  instead of ripgrep's regex engine.  Some advanced patterns (look-
  behind, Unicode categories) may behave differently.  Plugins and
  AI prompts that embed regex literals should prefer ECMAScript-
  compatible syntax.

* Grep performance: the Node.js grep walks files sequentially and
  reads each file into memory.  Files larger than 10 MB are
  skipped.  For large repositories the initial search response is
  slower than ripgrep, but the result format is identical.

* WebSocket proxy: the Bun proxy auto-detection for WebSocket
  connections was removed (patch-packages_opencode_src_plugin_openai_ws_ts).
  Users behind HTTP proxies that need WebSocket connections to AI
  providers will not have proxy applied to those connections.

* npm resolution (patch-packages_core_src_npm_ts): import.meta.resolve
  now always resolves only the directory, not package-name-relative
  paths.  This function is only used in the now-disabled plugin
  code path.  If plugins are re-enabled, this must be revisited.
